# Purview Teams PST → HTML Converter — Prioritized Fix Plan

Created: 2026-07-07
Author: Cursor agent review pass (working copy only; Hermes originals untouched)

**Goal:** Harden the PST→HTML converter and its GUI launcher, close correctness/robustness/security gaps, and optimize real conversion speed — without regressing the existing feature set, UX copy, or security posture.

**Architecture:** Two PowerShell scripts. `Convert-PurviewTeamsPstToHtml.ps1` (core, runs as **PowerShell 7** child) attaches a PST via Outlook COM, reads items recursively, and streams a self-contained HTML report. `Start-PurviewTeamsPstToHtmlApp.ps1` (launcher/GUI, runs as **Windows PowerShell 5.1**, compiled via PS2EXE) embeds the core as base64, launches it as a child process, and tracks progress.

**Tech stack:** Windows PowerShell 5.1 (launcher) + PowerShell 7 (child), WinForms, Outlook COM/MAPI, PS2EXE, embedded HTML/CSS/JS.

## P1 — Critical

### Task 1: Empty / participant-less PST no longer crashes
**File:** `src\Convert-PurviewTeamsPstToHtml.ps1` — `Write-ReportHeader` params (~886–891), call site (~1149), empty collections built (~1125–1133).
**Problem:** Array params are `[Parameter(Mandatory=$true)]`. PowerShell rejects an **empty** array on a mandatory param, so an empty PST (or one with no resolved participants) throws a binding error — or prompts/hangs under the windowless EXE.
**Change:** Remove `Mandatory` (or add `[AllowEmptyCollection()]`) on `$SortedRecords`, `$AllParticipants`, `$OtherParticipants`, `$ParticipantOptions`, `$OtherParticipantOptions`, `$FolderSummaryRows`.
**Verify:** Add a "no participants" sample path (or temporarily feed empty arrays) and run source `-NoGui -UseSampleData`; confirm a valid HTML report is produced instead of a binding error.

### Task 2: `-NoGui` no longer reports failure on success
**File:** `src\Start-PurviewTeamsPstToHtmlApp.ps1` (~223–225, with `$ErrorActionPreference='Stop'` at ~20).
**Problem:** `Write-Error $result.StdErr` is a *terminating* error under `Stop`; a child that exits 0 but wrote anything to stderr is caught and re-exits as code 1. Success looks like failure — breaks smoke tests/automation.
**Change:** Emit stderr non-terminating, e.g. `[Console]::Error.WriteLine($result.StdErr.TrimEnd())`; decide success strictly from `$result.ExitCode`.
**Verify:** Run source `-NoGui -UseSampleData`; confirm exit code 0 and `exported=3` even if the child emits stderr noise.

### Task 3: `-NoGui` stream read cannot deadlock
**File:** `src\Start-PurviewTeamsPstToHtmlApp.ps1` (~134–143).
**Problem:** Parent drains stdout to EOF, then reads stderr. If the child fills the ~64 KB stderr buffer, both hang forever.
**Change:** Read one stream asynchronously (`$proc.BeginErrorReadLine()` + an `ErrorDataReceived` handler accumulating into a buffer) before `WaitForExit()`; or run the stderr read on a background runspace.
**Verify:** Source `-NoGui -UseSampleData` still passes; optionally test with a child that emits a large stderr payload to prove no hang.

### Task 4: RPC retry covers item reads and PST detach
**File:** `src\Convert-PurviewTeamsPstToHtml.ps1` — item loop (~485), generic catch (~509), detach (~1256–1259).
**Problem:** `Invoke-OutlookComOperation` wraps startup/attach only. A transient `RPC_E_CALL_REJECTED` while reading item N silently *drops that message*; on `RemoveStore` it leaves the PST attached.
**Change:** Route `$items.Item($i)` (and ideally key property reads) and the `RemoveStore($root)` call through `Invoke-OutlookComOperation` so transient rejections retry instead of dropping/aborting.
**Verify:** Source `-NoGui -UseSampleData` passes (`itemReadFailures=0`); real-PST validation with Outlook briefly busy no longer drops items or leaves PST attached.

## P3 — Performance (actual conversion speed)

### Task 14: Cache COM `.Count` in subfolder/store loops (quick win)
**File:** `src\Convert-PurviewTeamsPstToHtml.ps1` (~525 subfolders, ~553 stores).
**Problem:** `.Count` is a COM call re-evaluated every iteration.
**Change:** Cache the count once before each loop (as already done for the item loop ~485 and attachments ~392).
**Verify:** Source smoke passes; behavior identical, fewer COM round-trips.

### Task 16: Single long-lived log `StreamWriter` (also fixes BOM)
**File:** `src\Convert-PurviewTeamsPstToHtml.ps1` — `Write-ReportLog` (~179–181), clear-at-start (~1208).
**Problem:** Log opened/closed per line; also `-Encoding UTF8` writes a BOM on 5.1/PS7 that can corrupt the GUI's tail parser.
**Change:** Open one `StreamWriter` with `UTF8Encoding($false)` (no BOM) for the run; write lines through it; dispose in `finally`. Folds Task 9's BOM fix into the perf change.
**Verify:** Log has no `EF BB BF` prefix; first line parses cleanly; smoke passes.

### Task 13: Stream records per-folder instead of full in-memory materialization
**File:** `src\Convert-PurviewTeamsPstToHtml.ps1` — record accumulation (~1217) and the write path.
**Problem:** Every message (body + pre-rendered attachment HTML) is held in memory before writing → memory ceiling and GC pressure on multi-GB PSTs. (Biggest real-speed item on large PSTs.)
**Change:** Emit conversations/records to the `StreamWriter` incrementally per folder/group rather than buffering the whole set. Preserve sort/grouping semantics (may require a two-pass or per-conversation flush). This is the largest task — scope carefully and keep the HTML contract intact.
**Verify:** Compare generated HTML on sample data (byte-diff of stable regions); confirm identical report structure; measure memory on a large real PST.

### Task 15: Compute participant display order once per conversation
**File:** `src\Convert-PurviewTeamsPstToHtml.ps1` (~1037–1046).
**Problem:** `Get-ParticipantDisplayOrder` / `Format-ParticipantPreview` / normalization run per **message** instead of per conversation.
**Change:** Compute the normalized/ordered participant set once per group before the `foreach ($record ...)` and reuse.
**Verify:** Report participant previews unchanged on sample data; smoke passes.

## P2 — Robustness / hardening

### Task 5: Run-ID + structured stdout progress model (root fix for stale-log + prose fragility)
**Files:** launcher `Start-EmbeddedConversionProcess` (~159), timer (~476–602), `Set-ConversionProgress` (~425–433); core progress emitters (`Write-ConversationProgress` ~190 and stage markers).
**Problem:** Progress is derived by regex-matching human-readable log prose and depends on a best-effort log delete; a single stale/foreign line + the monotonic clamp can lock the bar (e.g. at 96%) for a whole run.
**Change:**
1. GUI generates `$runId = [guid]::NewGuid()` per Convert; pass `-RunId $runId` to the child.
2. Core emits machine lines it already knows how to format: `CONVERSION_PROGRESS|RUNID=<guid>|STAGE=<name>|PCT=<n>|DETAIL=<text>` (reuse the existing structured channel that `Invoke-EmbeddedConversion` already parses at ~137–139).
3. GUI redirects **stdout** (`RedirectStandardOutput=$true`), consumes lines via an async reader/event, and **ignores any line whose RUNID ≠ current**. Keep monotonic clamp but gate it on run-ID-verified values only.
4. Keep the timer only for elapsed-time display; drop the per-tick full log tail.
**Resolves:** stale-log race (1.1/1.2), prose fragility (6.1), and UI-thread regex churn (7.1).
**Verify:** Stale-log regression test (pre-populate log with old cleanup lines) shows correct progression; wording changes in the core no longer break the bar.

### Task 6: Snapshot/disable path controls during a run
**File:** launcher `Set-ConversionControlsEnabled` (~445–451), timer (~485), completion (~569).
**Problem:** `$pstBox/$outputBox/$logBox` stay editable mid-run; editing them makes the timer tail a different file or "Open Report" open the wrong path.
**Change:** Snapshot the three normalized (`[IO.Path]::GetFullPath`) paths into `$script:activeConversion` at launch and use the snapshot everywhere; also disable the textboxes in `Set-ConversionControlsEnabled`.
**Verify:** Editing boxes mid-run has no effect on progress or the opened report.

### Task 7: Validate parent-dir existence + PST extension
**File:** launcher `Assert-GuiOutputPathsValid` (~453–469); PST check (~634).
**Change:** If output/log parent dir is not an existing container, throw a friendly error. Add a `.pst` extension sanity check for the input.
**Verify:** Nonexistent output folder is rejected before the child runs.

### Task 8: Kill child process tree + Job Object lifetime + Cancel button
**File:** launcher (~613–614 kill, ~617 FormClosing).
**Problem:** `$proc.Kill()` (no tree overload in .NET Framework) leaves grandchildren; a hard-kill of the launcher orphans the child + temp dir; no Cancel.
**Change:** Kill via `taskkill /PID <id> /T /F` (or CIM recursion). Bind the child to a Win32 **Job Object** (`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) so the OS reaps it if the launcher dies. Add a Cancel button reusing FormClosing kill/cleanup logic.
**Verify:** Cancel stops the child and cleans temp; killing the launcher in Task Manager leaves no orphaned `pwsh`/temp dir.

### Task 9: Log encoding fix (launcher side)
**File:** launcher `Get-Content` tail (~487, ~561).
**Change:** Add `-Encoding UTF8` to match the child's log encoding (core side handled by Task 16). Prevents garbled non-ASCII folder/error text.
**Verify:** Non-ASCII folder name displays correctly in progress/fatal text.

### Task 10: `Split-Path`/`New-Item` use `-LiteralPath` consistently
**Files:** core (~99, ~129, ~1200); launcher (~154, ~185, ~405, ~416, ~465).
**Change:** Switch `Split-Path -Path` → `-LiteralPath` and `New-Item -Path` → `-LiteralPath` so paths containing `[`/`]` don't misparse.
**Verify:** Validation/cleanup work with a bracketed test path.

### Task 11: Base64 decode-first with friendly corruption message
**File:** launcher `New-EmbeddedCoreScript` (~30–36).
**Change:** Decode into a byte[] first (cleaning `$tempRoot` on failure), then create dir + write. Wrap base64 failure in a "packaged converter is corrupted; reinstall" message.
**Verify:** Simulate a bad base64 var → friendly error, no leaked temp dir.

### Task 12: Remove `DoEvents` re-entrancy
**File:** launcher `Set-ConversionProgress` (~432–433).
**Change:** Replace `$form.Refresh()` + `Application::DoEvents()` with targeted `$progressBar.Update()` / `$progressLabel.Update()` to avoid re-entering the timer tick (double-completion/double-MessageBox risk).
**Verify:** No duplicate completion dialogs; progress still repaints smoothly.

## Per-change verification (from handoff checklist)

Primary dev loop (fast, source-level, no rebuild):
1. Parser-check core and launcher.
2. Run source `-NoGui -UseSampleData`; confirm `exported=3`, `itemReadFailures=0`, no `regular expression pattern` warning.
3. Grep generated HTML for the contract: report title, `participantMatchMode`, `startDateFilter`, `endDateFilter`, `sortOrder`, `conversation-toolbar`, `hero-credit` / `By Patrick Bush`, safe-encoded sample script text.

Milestone loop (before declaring a batch done):
4. Re-embed core into launcher (base64) if core changed.
5. Build debug + release EXEs into the working-copy `build` folder with version `1.0.27.0`.
6. Run debug EXE and release EXE `-NoGui -UseSampleData` smokes.
7. Stale-log regression test (pre-populate target log with old cleanup/final lines; confirm removed/superseded).
8. Manual GUI launch for any GUI-visible change (`-NoGui` does not validate the GUI).
